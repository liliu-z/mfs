# MFS 并发、恢复与 StashBase 接入审查

审查日期：2026-09-12。MFS 基准：`a872bde037c55041d9adb20ebed2ea9952c96f00`；StashBase 基准：`7c146e1c1aa1e017f45695ab49dd6f34136d9ee9`，同时读取其工作区当前实现。StashBase 已有未提交改动未作修改。

最初审查确认 7 个实现边界问题，以及“文件操作前的临时退休屏障”和“迁移原有用户意图”两个接入缺口。用户确认后，本工作区已修复上述问题并补齐 MFS 接口；实施结果见文末。下文保留修复前的复现与基准行号，现行合同以 [design.md](design.md) 为准。StashBase daemon 的实际迁移仍属应用后续工作。

**实现轴：已确认的问题**

1. **P1：删除事务提交后确认失败，旧执行可以复活已经持久删除的文档。**

   位置：[Lifecycle.remove](../src/mfs/_lifecycle.py)，661–665 行；同文件 `current`、`accept`、`persist` 可对照。

   `remove` 先提交 SQLite，再更新内存目标和 visible。若提交后抛出异常，它没有像 `accept/persist` 一样核对持久状态。复现时阻塞 Processor，提交删除后注入一次 StorageFailed，再放行旧 Processor：SQLite 中的目标先变为 delete，随后被旧许可提交回 upsert，read/search 再次返回被删除内容。已完成文档的版本也复现了 durable=delete pending、memory=upsert succeeded，搜索仍返回旧内容而 wait 立即成功。

   修复方向：统一所有状态命令的事务提交、确认失败核对、内存视图更新和执行许可失效。无法确认结果时，应停止旧许可提交，不能继续相信旧内存。drop、规则更新、cancel/retry、configure、request_rebuild 等相同形态的路径也需要覆盖；本次直接证实的是 remove。

   证据：`/tmp/mfs_review_lost_remove_resurrect.py`、`/tmp/mfs_review_lifecycle.py`。这是故障注入复现，不表示本次发生了自然磁盘故障。

2. **P1：External 转换期间修改源文件，会把错误文字写入处理缓存。**

   位置：[Preparation.prepare](../src/mfs/_preparation.py)，73–81、131–141、196–198 行。

   外部输入只在调用 Processor 前校验 hash，处理结束至缓存发布之间没有复核源身份/变动。确定性时序：sync 接受 alpha → Processor 进入后源变为 bravo → Processor 返回派生文字 `extracted bravo` → 结果缓存到 alpha 的内容键。之后正常 sync bravo，再把源恢复为 alpha 并 sync，Processor 不再执行，MFS 返回及搜索到的仍是 `extracted bravo`。总处理调用只有两次，第三次错命中缓存。

   这超出了“两次 sync 间允许索引落后”的合同：最终已重新 sync、源已稳定，错误结果仍会被缓存复用。

   修复方向：在处理结果和 checkpoint 成为可复用数据之前，绑定实际读取的源身份及版本；检测处理期间的变化，拒绝发布/复用不匹配结果。前后 hash 与文件身份/变动时间检查可作为基础，但同字节恢复的 ABA、分段 checkpoint 也须考虑。对于需要更强输入一致性的 Adapter，要明确其稳定读取合同；零复制不能意味着无条件信任可变路径。

   证据：`/tmp/mfs_review_source_race.py`，最终输出 `restored source alpha mfs text extracted bravo calls 2`，真实 BM25 仍命中 bravo。

3. **P1：POSIX 宿主被强杀后，受管理转换子进程仍能继续运行。**

   位置：[ProcessingContext.run_process](../src/mfs/processing.py)，123–135 行；[ProcessTree.close](../src/mfs/_platform.py)，130–132 行。

   子进程使用独立 session，正常退出/取消依靠 finally 中 killpg。宿主 SIGKILL 后该清理不再执行。真实复现结果：`host_exit_code=-9`、`managed_child_alive_after_host_sigkill=true`、`child_wrote_after_parent_death=true`；测试后已清理子进程。

   重启只恢复持久 target，不掌握这些仍存活的执行。据此推断，恢复同文档时可能同时存在新旧 OCR/转录执行；旧进程继续占 CPU/GPU、持有源句柄或写旧工作目录，GC 也不再知道它仍在使用文件。StashBase 的 `server/mfs-daemon.ts:405–421` 有 EOF → SIGTERM → SIGKILL 退出阶梯，会实际经过此路径。

   修复方向：明确进程树由谁跨 daemon 故障监管。采用父死清理/监督器协议，并在新代开始前确认旧后代退出；仅记录 PID 后直接 kill 也需要处理 PID 复用。增加 native helper 运行时强杀 daemon、重开、检查实际并发和文件租约的验收。本结论限定 POSIX；Windows 已有 Job Object 的 KILL_ON_JOB_CLOSE，未在本机验证其原生行为。

4. **P1：取消文件经历索引重建后，retry 沿用已失效的索引阶段。**

   位置：[Lifecycle.finish_rebuild](../src/mfs/_lifecycle.py)，607–624 行，尤其 612–613 行。

   重建清空 collection，却对 cancelled 目标整行跳过，保留旧 stage、plan 和 completed_batches。复现：在 publish 前阻塞 → cancel → reindex 完成 collection 重建 → retry。此时状态为 `cancelled publish rows=0`，随后稳定报 `publication is missing chunk rows`；继续 retry 仍从 publish 开始。文字仍可读，但正常重试不能恢复索引。embed 中途取消的同类状态还会保留已经不存在的批次进度。

   修复方向：保留用户取消门和 cancelled 状态，同时失效旧索引计划、批次及索引资格；已有兼容文字的目标回到 chunk，待显式 retry 后重建。process 阶段的 checkpoint 则单独按兼容性保留。

   证据：`/tmp/mfs_review_cancel_reindex.py`。

5. **P2：strong 搜索不处理失败终态，永久失败会占住查询容量。**

   位置：[ReadView.wait_ready](../src/mfs/_lifecycle.py)，1186–1214 行；[Reader.search](../src/mfs/_reader.py)，320–321 行。

   strong 只等待 pending 为空，failed/blocked/cancelled 仍都属于 pending。永久 Processor ValueError 后，wait(report) 立即返回 OperationFailed；strong(timeout=.15) 却等约 .154 秒，只返回 WaitTimeout。timeout=None 会一直等待。全实例查询容量为 4，四个这种等待即可占满容量，影响其他健康 namespace 的查询。

   修复方向：strong 与 current wait 共用失败终态判断，保留 revision、error code 和 cause，不能把已知永久失败伪装为尚未完成。暂停或尚未绑定依赖的等待策略也应明确。

   证据：`/tmp/mfs_review_lifecycle.py`。设计第 12 节已要求 strong/current wait 保留失败报错合同。

6. **P2：grep_path 指向本次 work_dir 时，会被 GC 删除。**

   位置：[Preparation.prepare](../src/mfs/_preparation.py)，153–166 与 190–195 行；[Catalog.references](../src/mfs/_catalog.py)，358–372 行。

   text_path 在 work_dir 内会复制为 owned 文件；grep_path 却无条件标记 owned=False。Processor 正常返回 `grep_path=context.work_dir / 'grep.txt'` 后，read 最初成功，GC 运行后工作目录文件被删除，read 报 SourceUnavailable。公开 ProcessedDocument 没有拒绝这个输入，ProcessingContext 还建议输出写在 work_dir。

   修复方向：统一两种文字引用的所有权处理；工作目录内的 grep 文件应复制并建立持久引用。若确实只支持外部借用 grep_path，应在接收时明确拒绝受管理临时路径，不能接受后静默丢失。借用外部文件的保留责任仍由宿主承担。

   证据：`/tmp/mfs_review_scan_gc.py` 第二部分。

7. **P2：一个子目录扫描失败，会阻止其他已确认区域的缺失清理。**

   位置：[sync_namespace](../src/mfs/_sync.py)，136–140、292–338、381–383 行。

   当前缺失判断依赖整个扫描的 complete。复现：先索引根下 gone.txt 和 denied/keep.txt，删除 gone.txt，再仅对 denied 子目录注入 PermissionError。根目录成功枚举，gone.txt 已明确不存在，但 report.removed 为空，排名搜索仍返回 gone.txt。只要那个无关子目录持续不可读，根级 sync 就持续不能清理此已知缺失。

   修复方向：记录成功观察的目录/范围以及失败前缀，在成功覆盖范围内处理缺失，只保护不确定区域。root 整体不可达仍应保护全部目标。现有逻辑偏保守避免误删，但没有实现设计所述的范围级故障隔离。

   证据：`/tmp/mfs_review_scan_gc.py` 第一部分。

**接入轴：两个需要先补齐的合同**

**文件改名、移动、删除之前的临时退休。** StashBase 当前 `server/file-operation-guard.ts:5–7`、`server/routes/folders.ts:112` 会先取消转换并等待源句柄释放，再改磁盘。接入文档的“应用改源，再 sync”缺少这一步。

MFS cancel 创建持久用户取消门；wait 对 cancelled 立即抛错。document_status.executing 能反映实际执行租约，因此宿主路径锁 + cancel + 轮询能够搭出屏障，但还需要保存原用户意图、失败补偿和崩溃恢复，否则临时文件操作变成永久用户取消。scope 轮询本身也不能阻止新任务领取。close 可以排空整个实例，代价是所有 Folder 一起停机。

建议明确一个 scope 的临时静止合同：停止新领取 → 等真实执行退出 → 执行源操作及补偿 → sync 新旧覆盖范围 → 释放临时限制；全过程不改变持久用户取消意图。可以由 MFS 提供可释放的 scope lease，也可由宿主实现，但只能有一个所有者。同一物理源映射到父子 Folder 时，要覆盖所有相关 namespace；播放转换仍归 StashBase，也要一起退休。

**首次迁移的用户意图。** StashBase 的转换状态持久保存失败/取消，`server/conversion.ts:615–624` 的发现逻辑阻止自动重跑。只创建新 namespace 并全量 sync，会让旧取消的 OCR/转录重新开始。MFS migrate_namespace 只升级自己的旧 catalog，不是 StashBase 旧单 collection 的导入器。

首次迁移需要日志和准入屏障：先保存 Folder 身份、规则、索引开关/暂停、取消/失败状态及配置，再开放处理。注意 configure_index(paused=True) 只暂停新增索引，**不会暂停 Processor**，不能用它充当迁移的准备准入屏障。可先保留宿主门或提供启动时的状态导入机制。迁移中崩溃后重放同一步骤，不应丢用户取消意图或重新执行昂贵任务。

**建议的接入方式**

先采用设计方案 A：一个 Python daemon 打开一个 MFS 实例；每个稳定 Library Folder ID 对应一个 External namespace；MFS 拥有处理、checkpoint、索引和恢复的当前目标。StashBase 保留文件操作、播放转换、业务规则、Viewer 和全 Library 的结果呈现。

| 现有职责/动作 | 接入安排 |
| --- | --- |
| Folder 注册、父子目录 | 稳定 Folder ID → namespace，保留各自独立根与规则；物理源变更同步全部相关 Folder |
| PDF/OCR/音频/HTML/JSON | 明确 Processor 路由，复用提取实现；按页/音频单元提交 checkpoint，不在 Processor 内等待另一套长期队列 |
| rename/move/delete | 先临时退休，再源操作；成功和回滚都同步新旧路径覆盖范围 |
| 手动 Sync、现有 MCP reindex | 主要映射 sync；需要恢复的失败目标显式 retry/reprocess，不能把应用名称直接映射为破坏性 MFS reindex |
| 模型/维度变化 | 按 Folder 显式 reindex；同 embedding space 的凭据轮换重新绑定 Adapter，不重做 OCR/转录 |
| daemon RPC | 保持读取请求与取消/状态可响应；长期 wait/reindex 放到有界执行层，不能阻塞串行 stdin dispatcher |
| keyword / semantic | keyword 保留 grep 与 fallback；semantic 映射 hybrid；全 Library 的 fan-out、超时预算、去重与排序由应用定义 |
| 文件/产物上限 | 旧 8 MiB 是索引文字上限；不要直接设为 namespace 的源文件上限，否则误拒绝大 PDF/音视频。Adapter 另限提取输出 |
| 依赖与打包 | 替换 mfs-cli 及旧私有 import，更新 sidecar hidden imports；新库要求 Python 3.13，现安装脚本仍接受 3.10 |

内置 Utf8TextProcessor 只路由 .md/.txt，sniff 返回 None；JSON/HTML 不能假定自动得到旧应用的处理行为。所有借用产物应使用与源 hash、处理配置关联的完整发布结果，并保证引用期间可读。

现有 StashBase 默认是 2 light / 1 heavy；当前 MFS 是一个文件 worker。checkpoint 改善调度响应，并不恢复轻重任务并行吞吐。建议先用有限 corpus 验证方案 A 的正确性和代价；若正式替换必须保留原吞吐，方案 B 的有界并发与资源容量就是上线前工作，而不能仅增加 worker 线程。它需要每文件排他、namespace 控制屏障、按执行持有的文件引用、Adapter 共享资源容量和查询 embedding 的统一计费。

如果过渡期必须保留 StashBase 的 Preparation 队列，则属于方案 C：必须先补按 incarnation/revision 限定、持久、可重放且不清用户取消门的完成通知，以及借用文件保留合同。现文档已经承认这些能力尚未实现，不应拿一次 retry 代替完整通知协议。

**建议实施次序与验收**

1. 先修删除确认、源版本/缓存、POSIX 子进程退出、cancel→reindex→retry 这四个 P1；再补 strong 失败、grep 引用和局部扫描隔离。
2. 明确源操作临时退休及迁移准入两个合同，连同 daemon 退出升级流程一起实现。
3. 用一个 Folder、TXT/JSON/PDF 和一个真实 Embedder 跑通 Adapter、RPC、规则及状态映射，再接 OCR/音视频。
4. 验收必须包含：处理期间改源；删/改名失败后回滚；父子 Folder 同源；取消后改模型再 retry；checkpoint/native helper 运行中强杀再重开；查询超时后重建/退出；GC 与仍被借用/使用的文件交错。
5. 通过真实 corpus 的首轮索引吞吐、短任务等待和交互搜索延迟，决定是否实施 B；全 Library 排名迁移另做 retrieval eval。

实现轴最严重的是持久删除可被旧执行覆盖；接入轴最重要的是没有明确源操作前的临时退休协议。当前已有的单 worker、namespace 独立、eventual 默认和查询超时后保留租约都是明确的设计选择，不应与上述实现漏洞混为一谈。

**确认后的实施结果**

| 原发现 | 工作区修复 |
| --- | --- |
| 状态命令提交后丢确认 | 统一事务核对、重载内存目标和撤销旧许可；核对本身失败则停止调度和结果发布，重开恢复 |
| 源变化污染缓存/checkpoint | 源 hash、文件身份和变动时间校验；checkpoints/完整结果发布前复核；索引读取再核对文字 hash；升级处理缓存格式 |
| POSIX 父死后遗留 native 执行 | 独立监督器通过管道检测父死，清理进程组，实际退出前保留继承实例锁；冻结入口支持私有监督分派 |
| cancelled → reindex → retry 失效 | 保留用户取消，已准备文字回到 chunk，清除旧索引计划与批次 |
| strong 永久等待失败目标 | 与当前任务 wait 共用终态判断，返回 OperationFailed 的 revision、state 和错误信息 |
| work_dir grep 引用被 GC 删除 | 复制为受管理文件，持久引用参与 GC 和缓存完整性校验 |
| 无关子目录失败阻止缺失清理 | 按成功观察目录与失败前缀分别判断缺失 |
| 源操作临时退休 | `quiesce` / `ScopeLease`：按创建代捕获范围，等执行与源读取退出；处理迟到读取、嵌套租约、超时和同名重建 |
| 迁移用户意图 | 持久 `processing_paused` 与 `restore_document_state`：准备前恢复失败/取消，校验当前 revision，重放不覆盖后来显式 retry |

正式回归见 [test_audit_regressions.py](../tests/test_audit_regressions.py) 和 [test_quiescence.py](../tests/test_quiescence.py)，包括真实 SIGKILL 宿主、重开恢复和确定性事务/源读取交错。最终完整验收结果记录在 [backlog.md](backlog.md)。

零复制仍不提供外部文件的原子快照；宿主自己的文件操作与 sync 需串行化并取得所有相关 namespace 的租约。POSIX helper 不得自行脱离受管理 session；实际冻结打包和 Windows 原生行为须在对应部署环境验收。单文件 worker 未扩为方案 B；方案 C 的宿主准备完成通知也未加入。
