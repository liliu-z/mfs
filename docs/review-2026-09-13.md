# MFS 当前实现与 StashBase 接入审视

> 以下为修复前的历史审视与实测，不代表修复后的当前结论。随后已将 R1–R8 转为正式回归并修复；另外补齐配置维护错误/同配置重试、丢失成员提交确认的恢复、交互优先级上限，以及 grep 与排名查询的容量隔离。独立复审又确认并推动修复了 sniff 持锁/FIFO 竞争、临时文字重建绕过 Processor 额度、晋升失败计数清零、删除后模型绑定残留四项。回归见 [test_review_boundaries.py](../tests/test_review_boundaries.py)，修复后的独立复审见 [independent review](review-2026-09-13-independent.md)。StashBase 应用迁移尚未实施。

审视日期：2026-09-13。MFS 基线为 `a872bde` 加当前工作区的全部未提交改动；StashBase 为 `7c146e1`，审视时工作区干净。未修改两边的实现；本次只增加这份报告与[复现脚本](review-2026-09-13-repro.py)。

**结论：主要职责划分已成立，但当前实现仍有会造成搜索漏结果、配置卡住及读取越界的问题，不适合直接替换 StashBase 的现有链路。** “已有并发、取消、恢复接口”与“全部用户流程已经可接入”是两件需要分别验证的事。

本次独立阅读了接收、当前目标/实际执行、配置代切换、搜索、扫描、准备、清理、GC、受管理子进程，以及 StashBase 的 daemon、检索、转换调度、播放和文件事务路径。以下先报告实现问题，再列应用需求与接入安排。

## 一、已复现的实现问题

### R1 · P1：旧快照在去重时遮住当前有效快照，搜索错误地返回空

位置：[后端命中去重](../src/mfs/_index.py#L519)、[之后才做可见性过滤](../src/mfs/_reader.py#L382)。

`ChunkIndex.search` 用 `(namespace, doc_id, ordinal)` 去重，未包含 `snapshot_id`。旧行尚未清理、新行已经发布时，如果旧行得分更高，会先留下旧行、丢弃新行；Reader 再过滤掉失效旧行，当前有效命中也就消失了。

真实 Milvus 复现：同一文件由 `old needle` 更新为 `new needle`，只暂停独立旧行清理，待新版本强一致就绪后做向量查询。后端有两行，当前文件的 `indexed_revision == revision`，结果却是 `SearchResult(items=(), truncated=False)`。

这不只是后台清理慢：只要旧查询持有 collection 租约，清理也会被正常延后；清理失败则可延长错误窗口。强一致目前也不能避免。应保留快照身份到有效性过滤之后，再做文档/片段去重。另需覆盖大量失效行挤满 1000 个候选的情况，避免把候选耗尽说成完整空结果。

### R2 · P1：重绑 Adapter 与配置晋升竞争，旧模型能覆盖新模型

位置：[open_namespace](../src/mfs/_core.py#L640)、[绑定写入](../src/mfs/_core.py#L670)、[配置晋升](../src/mfs/_configuration.py#L330)。

`open_namespace` 在读取旧配置后构建、验证绑定，再取得 lifecycle condition 写入。期间维护线程可以晋升候选配置；维护线程不受 `_mutation_lock` 约束，写入时也没有复核配置代。

复现顺序：候选 G1 正在 embedding → 开始绑定 G0、暂停在验证完成处 → 让 G1 完成并晋升 → 恢复 G0 绑定。调用成功返回，但活动配置已是 G1，运行对象却成为 G0；之后 vector search 持续抛 `NamespaceCompatibilityError`。

应在提交绑定时再次核对 namespace incarnation、目标配置代和清单，再原子采用；候选绑定分支也要覆盖“验证期间候选晋升/被替换”的窗口。不要通过在全局锁内加载模型来解决。

### R3 · P1：配置已持久接收，逐文件任务生成失败后不能靠重试同一请求补齐

位置：[配置接收与相同配置短路](../src/mfs/_configuration.py#L49)、[提交后的逐文件 synchronize](../src/mfs/_configuration.py#L99)、[任务落盘](../src/mfs/_configuration.py#L208)。

候选配置先提交 SQLite，随后逐文件创建 build target。后者任意一次存储失败，都可能留下有候选配置、却缺候选任务的状态。再次 `configure_namespace` 同一清单会直接返回 `changed=False`，后台维护只初始化 collection/尝试晋升，不补齐缺失任务。

故障注入复现：在候选文件目标的第一次写入抛一次 `StorageFailed`，随后恢复正常存储。再次提交同一配置，collection 已初始化，`build_targets` 仍为空，`wait` 超时；没有文件失败状态解释为什么它无法晋升。重开时构造路径会重新 synchronize，说明有恢复依据，但当前进程缺少持续恢复路径。

建议把“候选代已接收、成员任务尚未铺完”作为明确的持久状态，由有界后台批次幂等补齐。这样也能解决当前接收阶段长时间持全局锁的问题：在本机 3000 个已接收、处理暂停的文件上，仅更换 Chunker 声明，`configure_namespace` 用时约 **0.525 秒**，同期 `status()` 被阻塞约 **0.499 秒**，未运行真实转换或 embedding。这是该规模的实测，不是更大 corpus 的性能保证。

### R4 · P1：grep 没有执行总期限，普通文本也能明显超时

位置：[grep 的 timeout 使用](../src/mfs/_reader.py#L186)、[逐命中来源定位](../src/mfs/_reader.py#L258)、[全量扫描 SourceMap](../src/mfs/_documents.py#L43)、[Chunker 等待](../src/mfs/_runtime.py#L176)。

`grep(timeout=...)` 只将 timeout 传给 strong 的文字就绪等待，扫描、定位和 Chunker 执行没有共用 deadline。eventual 完全不用这个参数。`source_location` 对每个命中重新遍历全部 SourceSpan，代价约为“命中数 × span 数”；字节/匹配预算不能替代时间预算。

两种复现：

- 普通 UTF-8 文件仅 **140 KB、20000 行**，查 5000 个命中，`timeout=0.01` 仍耗时约 **2.9 秒**后返回。无需自定义慢 Adapter。
- `select="chunk"` 遇到未返回的 Chunker，超过 timeout 后仍等待，释放 Adapter 才结束。资源额度等待同样没有期限。

应明确 grep 的总等待合同并实现同一 deadline、有界执行与阶段检查；来源定位应利用有序区间索引或一次遍历批量定位。StashBase 的现有 keyword 路径使用可终止的 ripgrep，不能直接换成这个同步 grep 后宣称保留了搜索响应性。当前设计正文只为 ranked search 明确承诺总期限，这也暴露出 grep 参数语义不完整的问题。

### R5 · P1：External 源在 sync 后被换成符号链接，read/grep 会读取根目录外内容

位置：[grep 打开引用](../src/mfs/_reader.py#L155)、[read 的文字读取](../src/mfs/_artifacts.py#L131)、[读取资格只核对逻辑版本和规则](../src/mfs/_lifecycle.py#L1633)。

扫描使用 no-follow 和身份校验，但后续直接文字读取使用普通 `Path.open`。在 sync 与下一次读取之间，将 `root/a.txt` 换成指向 `root` 外文件的 symlink，`grep` 会命中外部文字，`read(DocumentId("n", "a.txt"))` 返回外部内容，并仍标注为原文档身份。已用临时文件复现。

应将 External 原源的安全打开封装为可复用模块：从已验证根逐段打开、拒绝不合格链接/特殊文件、核对实际身份和读取资格。读取资格需要在实际打开时成立。应用主动借用根外派生物是另一类合法引用，不能用一个简单“所有 text_ref 必须在 root 内”的判断误伤它。此问题尤其影响 StashBase/MCP 的授权目录语义；本次未声称当前 StashBase 的旧路径也存在同一问题。

### R6 · P2：一个不可读 External 文件让整个 grep 失败

位置：[逐文件读取未隔离失败](../src/mfs/_reader.py#L225)、[读取异常直接抛出](../src/mfs/_reader.py#L159)。

两个已接收文件都含关键词，删除第一个、暂不 sync，grep 直接抛 `SourceUnavailable`，第二个正常文件的命中拿不到。StashBase 本来就不是通过连续 filesystem watcher 保证文件永远不变，文件丢失、移动或云盘临时不可读属于需要处理的正常边界。

建议对宽范围 grep 返回正常命中和结构化 partial/failures，明确区分完整无结果与部分不可读。指定单文件 `read` 可以继续明确报错。不要把所有异常吞成空结果；quiesce 的范围阻断也应有明确的 partial 策略。

### R7 · P2：搜索在后端锁排队超时后，仍会启动过期后端请求

位置：[_SerializedClient](../src/mfs/_index.py#L92)、[取得 remaining 发生在锁外](../src/mfs/_index.py#L476)。

所有 namespace 的后端调用共用一把锁。SearchDeadline 的剩余时间在等待这把锁前计算；锁没有期限，取得锁后也不重新检查。用另一个后端调用持锁，search 先向调用方抛超时；释放锁后，底层 search 仍被真正调用，传入的还是过期前的预算。

已复现。调用方总超时有效，但过期排队工作仍会消耗后端、搜索槽与 collection 租约，延迟有效请求及清理/关闭。应把后端准入纳入 deadline，并在获得执行权后重算剩余时间。原生调用已经开始后无法即时终止的限制应保留，不应扩大到尚未执行的请求。

### R8 · P2：GC 将正常 SQLite 写竞争当作存储错误

位置：[GC 零等待写事务](../src/mfs/_artifacts.py#L285)、[异常统一进入 error](../src/mfs/_artifacts.py#L372)。

GC 主动设置 `busy_timeout=0` 以避让正常工作，但没有将 SQLITE_BUSY/LOCKED 归类成 `busy=True`。Worker 的产物登记等写事务可以在 lifecycle condition 外执行，正常并发就可能触发这里。

本次全量回归在 `test_staged_internal_request_cannot_overwrite_later_intent[update]` 失败，报 `catalog transaction failed: database is locked`；单独复跑两个参数用例通过。另用持有写事务的连接模拟 Worker 的写竞争，稳定得到 `busy=False, error=StorageFailed(...)`。现有证据说明它是并发避让/报告问题，未观察到因此丢数据。

应只把 SQLite 的忙/锁竞争映射为可再次尝试的 busy，保留损坏、I/O 等真实存储故障；补确定性的并发回归，避免仅依赖偶发时间窗口。

## 二、尚未闭合的设计与接入合同

### 1. 配置控制的恢复与可观测性

文件级 `retry` 不等于配置级恢复。候选 collection 初始化失败达到 5 次后，[initialize](../src/mfs/_configuration.py#L270)停止；相同配置提交短路，`retry(DocumentId)` 也不重置候选初始化失败预算。强制 `reindex` 能创建新一代，但这应当成为明确、可诊断的恢复流程，而不是让宿主猜测。

`namespace_configuration` 公开活动/候选清单与 revision，但不公开候选初始化错误、铺任务进度或退休故障；文件状态也不能完整表达这些 namespace 故障。需要统一定义候选配置的 status/retry/放弃方式，以及用户取消部分文件后如何恢复整代切换。可深化现有配置模块，不需要再造历史 operation receipt 系统。

### 2. 调度不能只对齐 heavy/light 的数字

StashBase [现有合同](../../stashbase/code-review/data-lifecycle.md#resource-bounds)是 interactive 优先，background 老化最多提升到 active-folder；[MFS priority](../src/mfs/_lifecycle.py#L729)直接用 `base_priority - age`，没有提升上限。后台等待超过两分钟时可以排在新 interactive 前。这是代码层面的策略差异，不是已测得的真实 corpus 等待时长。

StashBase 还拥有每文件 cost/classifier、队列展示，以及[同源播放优先中断转录](../../stashbase/server/audio-transcription.ts#L545)。MFS 的静态 Adapter resources 与非阻塞 Admission 只解决容量准入，未定义跨进程的任务身份、优先级、grant 撤销/过期恢复和播放交接。

接入时需要一个明确的容量所有者，Node 播放与 Python 准备共用 grant。grant 绑定 daemon generation/实际执行，真实退出后归还；RPC 超时不等于执行退休。播放抢占宜使用临时退休/恢复合同，不能映射成持久用户 cancel。查询与后台默认共享同一个 Embedder 的串行额度，[现有测试](../tests/test_concurrent_lifecycle.py#L214)本就允许背景 embedding 令查询超时；必须另验收前台容量与 provider deadline，不能把“5 秒报错”当作“搜索体验已满足”。

### 3. 关闭与失联要由进程级方案兜底

`close()` 明确等待真实 Adapter/原生执行退出；对于不返回的进程内模型或 Chunker，没有有限关闭保证。这种限制本身合理，但 StashBase 必须继续拥有单次退休流程、EOF/SIGTERM/SIGKILL 升级与有限重启预算，并实际验证 supervisor 持有 PROCESS_LOCK 的窗口。

Python/Node 各开一个线程池并不足够：若 Processor 等待 Node 响应，而 Node 的控制队列又等待该 Processor，会形成跨进程等待环。控制请求、宿主 grant/回调和耗时执行的调度合同必须一起确定。

### 4. 接入文档不能替代产品验收

[现有接入文档](stashbase-integration.md)对 namespace、取消、quiesce、迁移暂停和源事务已有合理安排。本次不会把已经实现的多 Worker、启动暂停、同名 namespace 创建代、向量缓存或 checkpoint 再列为“缺失”。缺口在上述实现问题，以及这些安排尚未进入 StashBase 实际链路。

## 三、StashBase 需求覆盖与建议接法

一个 Python daemon 持有一个 MFS 实例；每个稳定 Folder ID 对应一个 External namespace，包括父子重叠 Folder。StashBase 保留源文件与成员关系、权限、产品策略、Viewer/播放、全库结果呈现；MFS 负责已接收文档的准备、索引、版本失效与任务恢复。

| StashBase 需求 | 当前覆盖及接法 |
| --- | --- |
| TXT/Markdown/JSON/HTML 与准备文字 | TXT/MD 已内置；JSON/HTML 需应用 Processor。HTML 原文 grep 与提取后索引可分别提供。不能把上游 `upsert(text)` 机械替换成 External upsert，External 要走 sync。 |
| PDF/DOCX/OCR/音视频 | 接入实际提取器为 Processor。保留 PDF 完成标记、DOCX HTML、OCR 无文字成功、结构化转录 JSON+时间文字等产品要求；checkpoint 是恢复基础，不自动实现十分钟音频单元。 |
| 无 embedding 仍能浏览与精确搜索 | 可用 off/bm25、独立文字就绪状态；修复 grep 的期限与局部故障。保留经过验证的应用 fallback 和一致的输入规则。 |
| 前台目录语义搜索 | 单 namespace search；应用 semantic 意图通常映射 hybrid，默认 eventual。RPC 总预算从收到用户请求时开始，覆盖排队、模型和后端。超时明确呈现，不能返回“完整空结果”。 |
| 全 Library/MCP 搜索 | MFS 只搜一个 namespace，需要宿主有界 fan-out、共享总 deadline、partial 错误、重叠 Folder 归属/去重，以及明确的跨 Folder 排序。不能直接比较独立 collection 的 BM25/RRF 原始分数。当前 StashBase 的库级 semantic 入口仍需迁移，不能只验收 GUI 活动 Folder。 |
| keyword 行号、snippet、大小写、whole-word、类型过滤 | MFS 有对应基础筛选，应用需把 UTF-8 byte offset 转成 renderer 所用位置，保留 50 matches/file、500 total、snippet 截断等产品预算。应以现有 keyword 测试验证语义，不能只看字段同名。 |
| 源删除、改名、跨父子 Folder 移动 | 宿主路径锁 → 所有相关 namespace 范围 quiesce + 应用 Viewer/播放退休 → 磁盘操作 → content sync 新旧范围并检查 complete/failed → 记录接收完成 → 释放租约。wait 放在外面。 |
| 改名后的故障补偿 | 现有 [renameWithRollback](../../stashbase/server/rename-helpers.ts#L22)在 doIndex 失败时回滚磁盘。新链路以磁盘变更及完整 sync 接收为提交点；后续 embedding 失败不应再回滚已接收的文件操作。确需补偿时重新取得全范围租约并再次 sync。 |
| 删除 Folder 与共享产物 | drop 对应 namespace 并等待实际退休；不删除原件，不伤及仍登记的子 Folder/其他 Viewer。应用借用的派生物由应用保留至最后一个消费者退出，不能仅按某个 Folder 删除。 |
| 用户取消、失败和重试 | 持久 cancel 只对应用户意图；source-change/播放交接/shutdown 属于临时中断。同一物理文件涉及多个 Folder 时映射全部相关 DocumentId。 |
| 配置、密钥更换 | 相同 embedding space 的凭据更换重绑，不强制 OCR/转录或重新计算；模型变化走 configure_namespace 的候选代。需要先修 R2/R3，并定义配置失败的状态与恢复。 |
| 应用崩溃与迁移 | 宿主持久路径/迁移日志 + `MFS.open(start_paused=True)`；恢复磁盘实际状态、绑定两代配置、完成 sync 接收后 resume。首次迁移用持久 processing_paused 导入旧失败/取消；MFS 的 migrate_namespace 不读取旧 StashBase 数据库。 |
| 跨平台与打包 | 替换 mfs-cli 私有依赖和旧导入，使用 Python 3.13；冻结入口提前运行 supervisor 分派，打包所需模块，验证真实 OCR/转录子孙进程、进程锁和文件句柄。macOS 单测不能代替 Windows/冻结应用验收。 |

**当前 daemon 不能只换 handler 内的方法。** [Python dispatcher](../../stashbase/python/stashbase_daemon.py#L1950)同步执行 `handler(svc, args)`，Node 的[操作超时](../../stashbase/server/mfs-daemon.ts#L84)仍是 10 分钟。应改成按请求 ID 回应的有界并发执行，stdout 写入互斥；状态、取消、配置接收和宿主回调保持可响应。wait/reindex/sync 不能占住唯一控制执行通路。

建议顺序：先修 R1–R5，处理 R6–R8；落实配置恢复、调度与宿主事务合同；再用一个 Folder 跑通 TXT/MD/JSON/HTML/PDF 的真实 daemon 闭环，随后接 OCR/音视频、嵌套 Folder、旧数据迁移与冻结打包。保留现有接入文档中的范围划分即可，不需要为迁移新增跨 namespace 排名、filesystem watcher 或另一套通用准备队列。

## 四、验证与证据边界

- 原有全量回归：**162 passed、1 failed、3 skipped**，390.17 秒。失败为 R8 所述 GC 锁竞争；该参数化测试单独复测 **2 passed**，因此不能把一次重跑通过描述成问题已修复。
- 新增审视复现脚本：**9 passed**，24.35 秒，覆盖 8 类问题，其中 grep 有两种复现。脚本的断言用于确认缺陷存在，**通过不代表正确性验收通过**。最后一次普通文本 grep 用时 2.957 秒。
